## Design decisions

### Topic files own concept semantics and map geometry

A topic content entry is the canonical source for its name, summary, classification, maturity, relationships, frontier questions, papers, optional map position, and topic-page prose. Future topic pages and map components should derive from this collection rather than synchronize semantic data across topic and graph files.

### Use publication status as the canonical writing control

Writing status supports `draft`, `published`, and `archived`, defaulting safely to `draft`. An optional `draft` boolean is accepted for compatibility with the original conceptual schema, but it must agree with status. The normalized schema output always contains a boolean draft value.

### Keep relationship validation syntactic in this step

Schemas validate lowercase kebab-case IDs and duplicates. Cross-entry existence, duplicate topic IDs, missing map targets, and cyclic relationships require the full content set and belong to the map-data validation work in action item 10.

### Use structured manual paper links initially

Writing and topic entries accept paper title, URL, and optional year. This is sufficient for V1 and leaves room for the planned central paper registry without adding it prematurely.

### Test schemas with Node's built-in test runner

The Node.js 22 baseline can execute the TypeScript schema tests directly, avoiding another testing framework dependency for a small set of validation contracts.
