## Design decisions

### Keep all technical content static-first

KaTeX and Shiki run during the Astro build. The delivered HTML already contains accessible MathML, visible math, highlighted source, and language metadata. JavaScript adds only the copy button, so losing JavaScript does not remove or obscure the article content.

### Use Astro's unified processor for the established math plugins

Astro 7 defaults to its native Markdown processor. The project explicitly uses the official `@astrojs/markdown-remark` unified processor because `remark-math` and `rehype-katex` provide a mature, static math pipeline. MDX inherits the same Markdown configuration to prevent `.md` and `.mdx` from drifting apart.

### Let Shiki emit both theme palettes once

Each highlighted token contains light and dark CSS variables. Site theme selectors choose the active palette, avoiding duplicate code markup or runtime re-highlighting when the theme changes.

### Treat the copy control as optional enhancement

The button is absent from source HTML and is inserted only when the Clipboard API exists. The underlying `pre` and `code` elements remain selectable, labeled, and horizontally keyboard-scrollable in every case.

### Keep the rendering page as a temporary integration fixture

The `/rendering-test/` page provides a direct acceptance target until action item 7 introduces real articles. It uses a narrow test layout rather than anticipating the reusable article UI owned by action item 6.
