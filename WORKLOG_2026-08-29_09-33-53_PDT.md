## Design decisions

### Generate article routes from visible collection entries only

`getStaticPaths()` applies `shouldIncludeWriting()`. Production therefore emits only published, non-draft entries, while the route implementation remains compatible with development visibility rules.

### Treat the first topic as the primary breadcrumb path

An article may reference several topics, but a breadcrumb must be linear. The first topic in frontmatter is the primary conceptual path; every referenced topic still appears as a linked label in the article summary.

### Keep filters as optional progressive enhancement

The archive's full chronological list is static HTML. JavaScript reveals the filter controls, toggles the native `hidden` state, updates an `aria-live` result count, and maintains query parameters. No client framework or hydrated component is required.

### Derive filter choices from actual published content

Topic, format, and difficulty menus contain only values represented by visible articles. This prevents controls that can never produce a result before filters are combined.

### Use explicit control labels

Each select has an explicit `for`/`id` label association. This avoids accessible names that accidentally incorporate option text and gives browser and assistive-technology queries exact “Topic,” “Format,” and “Difficulty” targets.

### Keep topic URLs stable before topic pages arrive

Article and archive topic links already use `/topics/[topic]/`. Action item 9 will make those targets live without requiring article-content edits.

### Define maturity independently from publication status

Maturity describes how settled a concept is; publication status describes whether an article is draft, published, or archived. The content-model documentation now distinguishes foundational, established, active, and frontier concepts and notes that the labels should evolve with the field.
